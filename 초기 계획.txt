# 포켓몬 카드 이미지 인식 → 최저가/최고가 표시 (Web 우선) 기획/기술 스펙 정리

## 0) 요구사항(현재 확정)
- **플랫폼 우선순위**: Web (모바일 웹 포함)
- **주 타겟 시장**: **US / JP** (KR 우선 아님)
- **카드 언어**: **KO / JA / EN**
- **가격 표시**: **최저가(Low) / 최고가(High)** 2개만
- **핵심 플로우**: 사진(촬영/업로드) → 카드 식별 → 가격 조회 → 표시

---

## 1) 권장 전체 아키텍처(End-to-End 흐름)
1. 사용자 이미지 입력
   - 웹캠 촬영(getUserMedia) 또는 이미지 업로드
   - 모바일은 `input capture`도 병행(기기별 호환성 고려)
2. 카드 영역 탐지 + 원근 보정
   - 카드 사각형 탐지 → Perspective Transform → 정면 이미지로 정규화
3. 카드 식별(하이브리드 권장)
   - (A) OCR로 카드 **번호/세트코드/이름** 일부 추출
   - (B) 이미지 임베딩으로 **Top-K 후보 검색(벡터 검색)**
   - (C) OCR 힌트 + 후보 유사도를 결합해 최종 카드 1개 결정
4. 카드 정규화(표준 ID 확정)
   - 언어/세트/번호/레어도/변형(홀로/리버스/프로모) 분리
5. 가격 조회
   - 시장(US/JP)별 가격 소스에서 **low/high**만 조회
   - 캐시 적용 + 마지막 갱신 시각 저장
6. 결과 표시
   - 카드 메타(이름/세트/번호/언어/이미지) + **최저가/최고가** + **소스명** + **갱신시각**
7. 인식 실패 대응(중요)
   - 확신도 낮으면 **후보 Top-5**를 보여주고 사용자가 선택하도록 UX 설계

---

## 2) 추천 스택(웹 우선 / 확장 고려)

### 2.1 Frontend (Web)
- **Next.js + TypeScript**
- 카메라/업로드
  - Desktop: `getUserMedia` 기반 촬영 UI
  - Mobile: `<input type="file" accept="image/*" capture>` 병행
- 전처리(선택)
  - Canvas 기반 리사이즈/샤프닝
  - **OpenCV.js**로 카드 영역 탐지/원근 보정(클라이언트에서 1차 처리 시 UX ↑)

### 2.2 Backend
- **Node.js (NestJS) + TypeScript** 또는 **Spring Boot**
  - Spring 생태계 확장 계획이 있으면 Spring Boot 선택도 적합
- 비전/벡터 쪽만 **Python 마이크로서비스**로 분리하는 방식도 가능(선택)

### 2.3 DB / Cache / Vector Search
- **PostgreSQL**: 카드 메타, 외부 소스 ID 매핑, 가격 스냅샷, 인식 로그
- **Redis**: 가격 TTL 캐시, 인식 결과 캐시
- **Vector Search**
  - 초기: **FAISS(서버 내)** 권장(운영 단순)
  - 확장: Milvus/Pinecone 등 벡터DB로 교체

---

## 3) 인식(Recognition) 기술 스펙

### 3.1 카드 사각형 탐지 + 원근 보정
- 목표: 카드 이미지를 “정면”으로 펴서 OCR/매칭 정확도 향상
- 구현
  - OpenCV: edge/contour 기반 사각형 추정 + perspective transform
  - 실패 시 fallback: 중앙 크롭 → 후보 검색

### 3.2 OCR (부분 영역 ROI 권장)
- 전체 OCR보다 **번호/세트코드 위치 ROI만 잘라 OCR**이 정확도/속도/비용에 유리
- 옵션
  - 클라이언트: iOS Vision / Android ML Kit (웹 단독이면 서버 OCR 위주)
  - 서버: Tesseract(간단) / 클라우드 OCR(정확도↑ 비용↑)
- 다국어(KO/JA/EN) 고려
  - 언어팩/모델 선택 및 전처리(선명화/대비/노이즈 제거) 필요

### 3.3 이미지 임베딩 + 유사도 검색(Visual Search)
- OCR 실패/반사/각도 문제를 보완하는 핵심 백업 루트
- 플로우
  - 카드 공식 이미지(정면) 기준으로 임베딩 벡터 사전 생성
  - 입력 이미지 임베딩 → 벡터 인덱스 검색 → Top-5 후보 반환
  - OCR 힌트(언어/세트/번호)가 있으면 후보 필터링

---

## 4) 카드 메타데이터(카탈로그) 전략
- “무슨 카드인지”를 표준 ID로 확정하려면 카드 카탈로그가 필요
- 시작 전략
  - 공개 카드 API(카드/세트/이미지/번호)로 메타 확보
  - 이후 가격 소스의 productId(외부 ID)와 매핑 테이블 구축

---

## 5) 가격 데이터 소스 전략(US/JP)

### 5.1 US (권장)
- **TCGplayer API**
  - 가격 엔드포인트에서 **low/high** 같은 price points를 제공하는 형태
  - 운영 시 인증/쿼터/캐싱 정책 고려

### 5.2 JP (난이도 포인트)
- JP는 US처럼 “표준화된 공식 가격 API”가 깔끔하지 않을 수 있어 전략이 필요

**옵션 1) 집계 소스 기반으로 MVP**
- PriceCharting 같은 집계 API를 활용해 JP를 우선 커버(커버 범위/정의는 확인 필요)

**옵션 2) 상용 통합 API 사용**
- 여러 마켓을 묶어 제공하는 상용 API/서비스로 JP 커버를 노림
- 비용/약관/데이터 정의 확인 필요

**옵션 3) 직접 수집/제휴**
- 가장 강력하지만 차단/약관/운영 난이도↑
- MVP 단계에서는 비추천

---

## 6) “최저가/최고가” UX/정의 스펙(중요)
- 소스마다 low/high 의미가 다를 수 있음(리스팅 기반/집계 통계 등)
- 권장 표시 방식
  - `최저가 (SOURCE)` / `최고가 (SOURCE)`처럼 **소스명 고정 표기**
  - `마지막 갱신: YYYY-MM-DD HH:mm (KST)` 노출
- 통화 처리
  - US: USD, JP: JPY (필요 시 KRW 환산 옵션은 추후)

---

## 7) 캐싱/갱신(비용/쿼터 최적화)
- 카드ID + 시장(US/JP) + 언어 조합으로 캐시 키 구성
- **Redis TTL 캐시**: 1~6시간 권장(초기)
- 인기 카드 상위 N개는 배치 갱신(트래픽 대비)
- 저장
  - `prices` 테이블에 스냅샷 저장 → 추후 추세/차트 기능 확장 가능

---

## 8) DB 모델(예시)

### 8.1 cards
- `id` (PK)
- `name`
- `language` (KO/JA/EN)
- `set_code`
- `card_number`
- `rarity`
- `variant` (normal/holo/reverse/promo/…)
- `image_url`

### 8.2 market_product_map
- `card_id` (FK)
- `market` (US/JP)
- `source` (TCGplayer/PriceCharting/…)
- `external_product_id`

### 8.3 prices (스냅샷)
- `card_id` (FK)
- `market`
- `currency`
- `low`
- `high`
- `source`
- `fetched_at`

### 8.4 recognition_logs
- `id`
- `image_hash`
- `predicted_card_id`
- `candidates` (Top-K)
- `confidence`
- `elapsed_ms`
- `created_at`

## 9) MVP 체크리스트(바로 만들기)
1. 웹 업로드/촬영 UI 구현
2. 서버에서 카드 영역 탐지 + 원근 보정(또는 클라 1차 + 서버 보정)
3. OCR ROI 기반 번호/세트코드 추출(실패 시 스킵)
4. 이미지 임베딩 Top-5 후보 검색(FAISS)
5. 사용자 후보 선택 UX
6. US 가격(TCGplayer) low/high 표시
7. JP 가격(집계/통합 API) low/high 표시
8. Redis 캐시 + fetched_at 노출

---

## 10) 단계별 로드맵

### 1단계 (MVP)
- 업로드 → 후보 Top-5 → 확정 → US/JP low/high 표시 → 캐시/갱신시각

### 2단계 (정확도 향상)
- OCR ROI 튜닝, 반사광/흔들림 대응 전처리
- 언어/세트/번호/변형 정규화 강화
- 실패 로그 기반 개선 루프 구축

### 3단계 (JP 강화)
- JP 가격 소스 확정(통합 API 계약/제휴 등)
- 카드 변형(프로모/리버스/에디션/레어도) 분리 정교화
